Praktik · Deploy

Install Backend Laravel ke VPS

Goal: aplikasi bisa diakses di internet via domain, bukan cuma di localhost:8000.

Stack Production

Ubuntu 22.04 LTS Nginx PHP 8.3-FPM MySQL 8 Composer 2 Certbot (HTTPS) Supervisor (queue)

Langkah Deploy ke VPS

  1. Provisioning VPS — pilih provider (Niagahoster, Biznet, Hetzner), spec minimum 1 vCPU / 2 GB RAM / 40 GB SSD.
  2. SSH + Hardening — ssh root@ip, buat user non-root, disable root login, install UFW firewall.
  3. Install Stack — apt install nginx mysql-server php8.3-fpm php8.3-{mysql,xml,curl,mbstring,zip,gd,intl} composer git
  4. Clone Project — git clone <repo> /var/www/pos, composer install --no-dev --optimize-autoloader
  5. Setup .env Production — APP_ENV=production, APP_DEBUG=false, DB credential, php artisan key:generate
  6. Migrate & Cache — php artisan migrate --force, config:cache, route:cache, view:cache
  7. Nginx vhost — point root /var/www/pos/public, set fastcgi_pass ke PHP-FPM.
  8. HTTPS dengan Certbot — certbot --nginx -d pos.domainmu.com → auto-renew tiap 90 hari.

Nginx Vhost Snippet


server {
    listen 80;
    server_name pos.domainmu.com;
    root /var/www/pos/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_index index.php;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }

    location ~ /\.ht { deny all; }

    client_max_body_size 10M;
}

Setelah nginx -t + systemctl reload nginx → website live. Lalu jalankan chown -R www-data:www-data storage bootstrap/cache.

Common Gotchas Saat Deploy

1

Permission Storage

Folder storage/ dan bootstrap/cache/ WAJIB writable oleh user PHP-FPM (biasanya www-data). Kalau tidak → error 500.

2

APP_KEY Hilang

Generate fresh dengan php artisan key:generate. Tanpa ini, session dan encryption gagal.

3

Storage Symlink

Jangan lupa php artisan storage:link untuk akses upload via URL.

4

APP_DEBUG=true di Prod

EXPOSE stack trace + DB credentials ke publik. Wajib false di production.

Fitur 01

Cash Session — Konsep

POS profesional WAJIB tracking duit fisik per shift. Tanpa ini, kalau ada selisih, tidak ada cara accountable.

Flow

  1. Buka Shift — kasir input modal awal (opening_float) + label shift (Pagi/Siang/Malam).
  2. Order otomatis attach ke shift aktif (via Model boot event).
  3. Tutup Shift — kasir hitung fisik di laci → server hitung expected → simpan variance.
  4. Force Close — admin bisa paksa tutup kalau kasir lupa.
Variance = physical_count − (opening_float + cash_in − cash_out + cash_revenue)

Cash Session — Schema


cash_sessions
├── id, user_id → users
├── shift_label (Pagi/Siang/Malam)
├── opening_float, opening_note, opened_at
├── cash_in, cash_out
├── physical_count, expected_cash, variance
├── closing_note, closed_at
└── timestamps

INDEX (user_id, closed_at) → quick "current session" lookup

orders
└── + cash_session_id → cash_sessions (nullable)

Detail step ada di docs/16-cash-sessions.md

Fitur 02

Promo — 3 Tipe Diskon

A

Percent

Diskon 1-100% dari subtotal.
Contoh: WEEKEND15 = 15%

B

Rupiah

Potongan rupiah tetap, min(value, subtotal).
Contoh: NEW5K = Rp 5.000

C

B1G1

Buy 1 Get 1: untuk tiap qty ≥ 2, diskon = harga × floor(qty/2).

Validasi Server-Side

isLive() check active starts_at ≤ now ≤ ends_at subtotal ≥ min_subtotal computeDiscount() = single source of truth

Flutter app TIDAK boleh hitung diskon sendiri — selalu hit POST /api/promos/apply.

Fitur 03

Refund Flow

Refund bukan cuma update status — ada 3 efek yang harus konsisten:

  1. Mark Order — status = REFUNDED, simpan refund_reason, refund_note, refunded_by_user_id.
  2. Restore Stok — untuk tiap order_item: Product::increment('stock', $qty).
  3. Reconciliation Shift — cash_session.cash_out += refund_amount agar variance shift tetap balanced.

Semua dilakukan dalam DB::transaction() — atomic. Hanya Owner yang boleh refund (via OrderPolicy::refund).

Fitur 05

Play Store Compliance

Google Play 2024+ WAJIB punya 2 hal kalau app mengumpulkan data user:

A

Privacy Policy URL

Public URL yang bisa diakses tanpa login. Di kita: /privacy di domain backend.

B

Account Deletion

User harus bisa hapus akun dari dalam app, tidak cuma minta email. Endpoint: DELETE /api/account.

Pattern Aman: Anonymize + Soft Delete


DB::transaction(function () use ($user) {
    $user->forceFill([
        'name' => '[akun dihapus]',
        'email' => 'deleted-'.$user->id.'@deleted.local',
        'avatar' => null, 'phone' => null, 'is_active' => false,
    ])->saveQuietly();
    $user->tokens()->delete();   // revoke semua API token
    $user->delete();             // soft delete
});
Fitur 06

Security Fix: Back-Button Logout

Bug: setelah logout, tekan back-button browser → halaman authenticated MASIH muncul (dari cache).

Vulnerable

Route::middleware('auth')->group(function () {
    // halaman authenticated...
});
Fix

Route::middleware([
    'auth',
    'cache.headers:no_store;no_cache;must_revalidate;max_age=0'
])->group(function () { ... });

Header HTTP Cache-Control: no-store paksa browser fetch ulang, bukan ambil dari history.

Framework Prompt yang Efektif

Prompt asal-asalan = output asal-asalan. Pakai struktur 5-bagian:

  1. Context — "Saya punya Laravel POS project di /path. Stack: Laravel 13, Sanctum, Stisla theme."
  2. Goal — "Saya mau bikin fitur X yang melakukan Y untuk user Z."
  3. Constraints — "Gunakan pattern existing: FormRequest untuk validasi, Resource untuk API response."
  4. Verification — "Test dengan curl POST endpoint A → expect status 201 dengan field B, C."
  5. Explanation — "Setelah generate, jelaskan kenapa pilih approach itu, dan trade-off-nya."

Demo: Tambah Fitur Loyalty Point

Goal: Customer dapat poin per Rp 10.000 belanja. Redeem 100 poin = diskon Rp 10.000.


PROMPT ke Claude AI:

"Saya punya Laravel POS project. Stack: Laravel 13, Sanctum, Bootstrap+Stisla.
Schema lengkap ada di docs/07-models-migrations-pos.md.

Tolong tambahkan fitur Loyalty Point:

1. Migration: tambah tabel `customer_points` (id, customer_phone, balance, timestamps)
   dan tabel `point_transactions` (id, customer_phone, order_id, type[earn/redeem],
   amount, timestamps)

2. Logic: saat order create, kalau ada customer_phone → earn 1 poin per Rp 10.000 subtotal.
   Saat order create dengan redeem_points → kurangi balance, hitung diskon Rp 100 per poin.

3. API endpoint: GET /api/customers/{phone}/points → balance + recent transactions

4. UI: di order detail web, tampilkan poin yang earned/redeemed.

Ikuti pattern existing: FormRequest, Resource, Policy, helper rupiah().
Generate dengan DB::transaction. Jelaskan setelah jadi kenapa pilih schema seperti itu."
